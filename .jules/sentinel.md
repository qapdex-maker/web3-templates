## 2025-02-18 - Client-Side DOM-Based XSS in Static HTML Templates
**Vulnerability:** In static interactive Web3 HTML templates using Tailwind CSS, user input retrieved from textarea/input elements is rendered directly via `innerHTML` into the DOM. This allows arbitrary JavaScript execution (Cross-Site Scripting) if an attacker inputs malicious HTML tags or script blocks.
**Learning:** Because the templates are standalone client-side HTML files without any backend server or node packages (no build steps, no external sanitization packages), standard sanitization libraries like DOMPurify or server-side escaping are not readily available or integrated. Developer relies on fast, lightweight vanilla JavaScript templates where `innerHTML` is mistakenly used to build UI components dynamically, creating a high-risk security gap in user input presentation.
**Prevention:** Always implement a dedicated utility function to escape special HTML characters (`&`, `<`, `>`, `"`, `'`) within the script blocks of any template doing client-side rendering. Prior to setting `innerHTML` with dynamic user text, wrap the user input with the escape function, or use safer APIs like `textContent`/`innerText` where raw HTML rendering is not strictly necessary.

## 2025-02-19 - Client-Side Credential Exposure in iframe Integrations
**Vulnerability:** Integrations with third-party iframe embed services (such as Microsoft Bot Framework Webchat) often utilize API keys or secret tokens passed via query parameters in the URL (`?s=SECRET`). Hardcoding these secret tokens or secret placeholders directly inside static client-side HTML templates inevitably exposes them to anyone viewing the source code, leading to credentials leaks or git history exposure if committed.
**Learning:** Client-side-only static mockups lack backend proxy servers or environment-variable injection layers. Developers frequently hardcode API keys or secret placeholders directly in the markup to quickly showcase feature functionality, inadvertently paving the way for developers to replace them with live production credentials that are subsequently committed to version control.
**Prevention:** Avoid embedding secrets directly in any static client-side HTML markup. Instead, build a dynamic token activation screen in the UI with a masked password input field, store the activated secret securely in browser `localStorage`, and dynamically inject the iframe element into the DOM using JavaScript, while ensuring appropriate `sandbox` and `referrerpolicy` restrictions are set for defense-in-depth. Always provide a clear/reset action to purge credentials from local storage.
